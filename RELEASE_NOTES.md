# ClickHouse 0.0.1-draft — Beta

Initial beta prerelease of the native Crystal ClickHouse shard. Public APIs and
compatibility guarantees may change before a stable release. Requires Crystal
1.21.0 or newer; install with `version: 0.0.1-draft`.

## Native driver

- Crystal-owned TCP and verified TLS transport, password authentication,
  certificate/hostname checks, IO timeouts, and query deadlines.
- Native protocol revision 54460, with minimum server revision 54459, bounded
  binary readers, Hello/Ping, settings, typed parameters, metadata, and errors.
- Materialized results, row/block streaming, progress callbacks, owned values,
  and explicit single-operation connection ownership.
- Server-schema-guided binary inserts through row-oriented `Batch#append` and
  direct-columnar `Client#insert_blocks`, with typed arrays, bounded blocks,
  duplex error handling, and caller-owned block retention.
- Pure Crystal LZ4 and ClickHouse CityHash128 1.0.2, validated frame sizes and
  checksums, and interoperability fixtures from independent implementations.
- Int/UInt8–128, Float32/64, Bool, binary String/FixedString, Nullable/Nothing,
  Date/Date32, DateTime/DateTime64, Decimal32/64/128, UUID, IPv4/IPv6, Enum8/16,
  Array, Tuple/named Tuple, ordered duplicate-key Map, and supported per-block
  LowCardinality dictionaries.
- Interrupted or failed operations discard their connection. Transport loss
  after insert data is sent can return `InsertOutcomeUnknown` with its query ID;
  SQL and inserts are never replayed automatically.

## Examples

- Standalone connection, streaming-query, binary-batch, and analytical-value
  applications, each with its own manifest, lockfile, and instructions.
- A standalone Kemal OpenRTB ingestion API with `POST /ortb/bids/bulk` and
  paginated `GET /ortb/bids`, UTC-day or explicit-timezone range filters, native
  columnar persistence, handler-level dependency injection, and a MergeTree
  schema ordered by receipt time and ingestion UUID.
- Validated bulks of up to 10,000 requests, complete semantic JSON payloads,
  Docker setup, separate handlers/entities/repositories, and HTTP/persistence specs.
- An opt-in local benchmark outside CI: 1,000,000 independently randomized
  OpenRTB records per mode, 100 inserts of 10,000 records, identical seeded
  datasets, separate generation timing, and exact persistence verification.

## Validation

- 65 deterministic specs, formatting, and Ameba checks pass.
- 44 integration specs pass for each LTS/stable × none/LZ4 combination, including
  plaintext and verified TLS, against pinned official ClickHouse 26.8.31.2 LTS
  and 26.9.22.3 stable images on arm64.
- The Kemal example passes 69 in-memory specs and 70 real-server specs, including
  a 10,000-request HTTP bulk and date/time boundaries.
- Both million-record benchmark modes pass count, UUID uniqueness, impression
  totals, payload-size, sample-value, and matching payload-hash checks. One local
  release-mode LZ4 run measured approximately 180,000 records/second per mode;
  this is a local observation, not a general throughput guarantee.
- Independent Python native-protocol probes and upstream-generated byte fixtures
  verify behavior beyond encoder/decoder self-round-trips. GitHub Actions
  configures the corresponding amd64 checks; local results above are arm64.

## Beta limitations

- No connection pool, crystal-db adapter, ZSTD, external tables, transactions,
  async INSERT, Int/UInt256, Decimal256, AggregateFunction states, or native
  JSON/Variant/Dynamic codecs. Shared LowCardinality dictionaries are rejected.
- A primary/sorting key does not enforce uniqueness. The example is append-only;
  partial bulk failures can leave completed batches, and offset pagination plus
  separate count queries do not provide a snapshot across concurrent writes.
- ClickHouse text parameters in the negative fractional epoch interval between
  -1 and 0 seconds are rejected to prevent incorrect DateTime64 values. Use exact
  Int64 ticks with `fromUnixTimestamp64Milli/Micro/Nano`; Native binary timestamps
  preserve that interval.
- Compatibility is claimed for the tested server releases and protocol ceiling;
  the protocol floor alone does not establish support for every older release.
